# Gamblock AI — Browser Extension

Chromium/Firefox Manifest V3 extension that acts as a passive DOM sensor for
Gamblock AI on Windows. It reads limited textual page data and relays it to the
local Windows Service for on-device classification. Chromium-family browsers
use `manifest.json`; Firefox uses `manifest.firefox.json`. Browser support is
derived from the extension/WebExtension APIs and the authenticated source
context, not from a browser-name allowlist. Per-browser runtime evidence is
still required before a browser/version is called verified.

## Safety boundary

This extension:

- extracts the page title, up to 10 headings, and up to 50 anchor texts;
- extracts **only on committed actions**, never while the user types: page
  load, committed URL change (navigation), an Enter key press (excluding IME
  composition), or a form submit;
- coalesces bursts from those committed actions with a 50 ms local debounce so
  the Windows protection path can stay within its sub-200 ms target;
- accepts a scan only from the active top-level tab in the focused browser
  window, while keeping tab/window identifiers in volatile extension memory;
- relays the snapshot to `ws://127.0.0.1:9090` only after a mutual HMAC-SHA-256
  challenge using the pairing token; the token itself is never sent;
- does not classify content, block pages, redirect tabs, or display Pattern
  Interrupt UI;
- does not send DOM text, URLs, domains, or browsing history to a remote server.

Classification, blocking, and Pattern Interrupt belong exclusively to the
separate Windows Service. This repository implements and tests the sensor side;
end-to-end protection requires that peer service to be installed and running.

## Local development

Requirements: Node.js 20+ and npm.

```sh
nvm use
npm ci
npm run lint
bash scripts/verify-ai-context.sh --allow-untracked
```

Tests and package/smoke verification are available but run by the AI only when
the user explicitly requests them.

To try the unpacked Chromium extension:

1. Open `chrome://extensions` or `edge://extensions`.
2. Enable Developer mode.
3. Choose **Load unpacked** and select this repository directory.
4. Open the extension options page and save the pairing token generated by the
   Gamblock desktop client.

For Firefox development, stage the Firefox package with
`bash scripts/package-extension.sh firefox`, then load the resulting ZIP as a
temporary add-on. Store-distributed production installs must use the signed
Chrome Web Store, Microsoft Edge Add-ons, or Firefox Add-ons artifact.

## Files

- `manifest.json` — Chromium MV3 configuration and runtime asset references
- `manifest.firefox.json` — Firefox MV3 configuration with the stable Gecko ID
- `background.js` — MV3 orchestration for the authenticated local relay
- `background/` — small modules for bounded snapshots, pairing storage, and
  local WebSocket lifecycle
- `content_script.js` — classic content script for passive DOM extraction
- `options.html` / `options.js` — pairing-token configuration
- `_locales/` — Indonesian and English extension messages
- `images/icon.png` — icon used at 16, 48, and 128 pixels
- `scripts/` — context, manifest, release-package, and release-metadata verification

## Permissions

The manifest currently declares:

- `storage` — stores the local pairing token;
- `alarms` — wakes the MV3 service worker to restore the local connection;
- `tabs` and `activeTab` — tab context required by the extension runtime;
- `<all_urls>` host access — runs the passive content script on navigated web
  pages so previously unknown gambling domains can still be inspected locally.

Any permission expansion must be justified in both `manifest.json` and this
section. The extension must never use these permissions for remote telemetry or
for blocking/redirecting a page.

The Firefox store disclosure declares required `websiteActivity` and
`websiteContent` processing because the extension sends the current URL and
bounded page text outside the extension process to the local Windows service.
That data remains on the device, is transient, and is never sent to a remote
service.

## Pairing flow

1. The Gamblock desktop client generates a pairing token.
2. The user opens the extension options page.
3. The user pastes and saves the token in `chrome.storage.local`.
4. `background.js` reconnects and completes mutual challenge-response
   authentication before relaying DOM scans. A bounded, in-memory scan queue
   may wait for the current
   authentication handshake; it is never persisted and is discarded when the
   connection closes or pairing is absent, replaced, or denied.
   A rejected token is not retried until the user saves a new pairing token.

## WebSocket protocol

Connection: `ws://127.0.0.1:9090`

1. Service sends `{ "type": "server_hello", "protocol": 2, "server_nonce" }`.
2. Extension responds with `{ "type": "auth_response", "protocol": 2,
   "extension_id", "client_nonce", "proof" }`. `proof` is HMAC-SHA-256 over
   the protocol version, both nonces, and extension ID using the pairing token.
3. Service replies with an independently keyed `auth_ok` proof, or sends
   `auth_denied` and closes the socket. The pairing token never crosses the
   socket.
4. On authenticated connections, the extension relays DOM scans as
   `{ "type": "dom_scan", "scan_id", "url", "title", "headings", "anchorTexts", "extractionDurationMs", "scanStartedAtMs", "timestamp" }`.
   `extractionDurationMs` is a bounded local performance measurement used only
   by the opt-in Phase 4 latency evidence path. `scanStartedAtMs` is used only
   in memory to bridge the extension/service clocks and is never written to
   evidence. Neither field contains page content or reaches the backend.
5. Before the Windows agent performs a browser action, the service sends
   `{ "type": "context_probe", "probe_id", "scan_id" }`. The extension
   returns only `same_active_focused`, `navigated`, `closed`, `source_lost`, or
   `unknown`. Tab and window IDs never cross loopback IPC.
6. The service must never instruct the extension to block or redirect; that
   authority stays in the local Windows Service.

Changing these message shapes requires a coordinated change with
repository `Gamblock-AI-Apps`
(`https://github.com/Gamblock-AI/Gamblock-AI-Apps`), peer-relative path
`windows/service/protection_service_websocket.cpp`.

## Packaging

Create and smoke-test the release archive with:

```sh
npm run package:extension
npm run verify:package
```

Packaging creates separate `chromium` and `firefox` ZIP files. Each includes
the selected manifest as `manifest.json`, background/content scripts, options
page, all `_locales/` catalogs, and `images/` assets. Package verification
extracts both ZIPs and verifies every manifest-referenced file.

Tagged releases use the immutable `vMAJOR.MINOR.PATCH` tag as the extension
version. Both manifests must contain the exact tag version; the release job
fails before upload when they differ. The GitHub Release also contains a
`gamblock-ai-extension-SHA256SUMS.txt` file and a
`gamblock-ai-extension-compatibility-v<version>.json` sidecar describing the
package hashes and the Windows loopback WebSocket protocol version. These
sidecars are release metadata only and are not submitted to browser stores.
Extension releases are versioned independently from the Flutter Apps release;
the compatibility sidecar records the stable protocol boundary without making
either release depend on the other.
